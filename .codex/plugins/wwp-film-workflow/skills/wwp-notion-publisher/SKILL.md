# WWP Notion Publisher

Publish playable outputs and prove the library state. Prefer existing WWP repository tools over rewriting Notion API logic.

## Workflow

1. Confirm the work page or create one only when the work is genuinely new.
2. Reuse existing work pages for supplemental specs.
3. Title every newly created or currently touched spec page with the canonical grammar from `../../references/notion-media-assets.md`: short canonical Chinese work title, explicit original/dubbed audio label, explicit subtitle treatment, measured resolution, codec, and exact decimal-GB display size, in that order. Do not repeat the parent English/original title or year, omit the audio nature, or use internal high/medium/low tier words.
   Derive the displayed size from the exact final file byte count using the workflow's decimal-GB convention. Do not inherit a stale size from a filename or an existing placeholder page; a materially different size requires a corrected or separate spec page.
4. Create or reuse the target spec page before encode starts whenever manual upload may be needed. A reused movie spec page is a valid destination only when it contains no video block. If it already contains media, report the existing asset and stop the new encode unless a deliberately distinct specification has been approved. Notion API cannot move an already uploaded media block into a different child page in this workflow; report the target page ID before the user uploads and do not rely on later root-level cleanup.
   An explicit movie `--target-page-id` or series `--target-spec-page-id` must be re-enumerated under the requested work/series page immediately before upload. Refuse a target outside that parent, even if the supplied page ID exists. Supplying only a spec title is insufficient; use the exact checked ID, or use explicit `--create-spec` during structure creation. Never let an upload command implicitly select or rename the first existing spec page.
5. If the work page/spec page exists but upload is slow, deferred, or not yet suitable, route to `wwp-metadata-backfiller` immediately and continue upload work afterward or in parallel.
6. Upload playable MP4 files automatically with the mapped repository tool by default. For series, upload one file to each Episode page unless collection delivery was explicitly requested. Before creating any upload session, enumerate every selected Episode target: an existing video block, including an unnamed Notion-hosted block, is a hard stop for that Episode and the batch. Inspect and reconcile it first; never upload a second file merely because the existing block has no filename/caption. Use a manual-upload handoff only after the route preflight is too slow, bounded automatic retries fail, or the user explicitly chooses manual upload; name every prepared destination page and ID.
7. Before any Notion access or transfer, probe each final local file. Reject a video with no video stream and reject HEVC/MP4 unless `codec_tag_string=hvc1`; losslessly remux `hev1` to `hvc1`, then re-probe it. This is a pre-upload gate, not a later Media Assets correction.
8. Before a large API upload, run a small multipart route probe with the normal `api.notion.com` hostname. On Clash-based hosts, verify that the connection matches `Notion -> 国内直连 -> DIRECT`, not `Match` or any paid proxy group. A non-`DIRECT` route is a hard stop unless the exact controlled Freedom s801 exception below was selected for this run. Do not start, continue, or retry a large transfer through an ordinary proxy because it can consume the traffic allowance. Use at least `2 MiB/s` as the default safe-start floor for a near-5GB file; below that, stop before consuming the one-hour upload window.
   If an unbound direct upload starts materially below that floor, stop it early rather than waiting for the one-hour session to fail. Re-resolve the current Notion API address and retry the same resumable manifest with `--resolve-ip <api-ip> --local-address <physical-lan-ip> --no-proxy` only. Never pass `--resolve-ip` by itself: the raw IP loses Clash's Notion domain match and can fall through to a paid proxy group. Previously accepted multipart parts must be reused. Re-detect both addresses for every run and retain concurrency 1; the measured improvement is evidence for that run only, not a permanent hardcoded route.
   If an accepted DIRECT multipart session later degrades, first recycle only that uploader's connection and resume the same `file_upload_id` from the last accepted `part_number`. Give a bounded number of fresh DIRECT connections a chance to restore throughput before considering s801; never discard accepted parts or restart the whole file merely to obtain a different connection. Consider s801 only when those same-route resumable retries still cannot finish inside the current upload expiry, or when protecting the ordinary allowance is the explicit reason for the batch.
   When `VPN_TRAFFIC_CHECK_URL` or `VPN_TRAFFIC_CHECK_URL_2` is configured, take a counter baseline before the probe/upload, sample at bounded intervals during accepted multipart progress, and sample once at completion. The current first endpoint is the long-lived LA/JMS allowance and resets on day 2; the optional second endpoint is the temporary London allowance and may be removed after it expires. Never persist or print either secret counter URL. Persist only labels, counters, reset days, deltas, upload progress, and risk classification in the adjacent `.vpn-traffic.json` report.
   Traffic-counter growth is corroborating evidence, not a route verdict: friends may use the same allowance concurrently. Do not stop a route that still has explicit Clash `DIRECT` evidence merely because a counter increased. Report material or upload-correlated growth, and warn the user when sustained growth projects exhaustion before the provider reset or when the remaining allowance is smaller than the suspected routed remainder. If Clash shows a non-`DIRECT` route other than the exact approved s801 chain, the existing hard stop remains authoritative.
   **Controlled Freedom s801 exception:** JMS Freedom server `s801` may be considered when a necessary high-volume transfer cannot reasonably complete over DIRECT after the bounded same-route resumable retries above, or proactively when a large transfer is unavoidable and protecting the ordinary monthly allowance is the explicit reason for the batch. It is not an automatic fallback or a default route. A configured s801 node does not prove that traffic uses it. A selectable s801 member inside the existing node group is sufficient; a separate routing rule or dedicated s801 group is not required. Do not require or create a dedicated permanent s801 route merely because none exists: use `node tools/with-notion-upload-route.mjs --route jms-s801 --reason <estimated-batch-size-or-direct-failure> --apply -- <probe-or-upload-command>` to discover the current Clash selector topology, save both existing choices, temporarily set the existing `Notion` selector to `JMS London 节点` and that nested selector to the unique `s801` member, then read both values back from the controller. The expected readback chain is `Notion -> JMS London 节点 -> JMS London s801 - Reality`. If the selector or node names differ, discover a unique `s801` member and verify the resulting chain; stop when it is missing or ambiguous instead of guessing or editing the permanent profile. A generic `JMS London 节点`, `JMS London 自动`, `规则代理`, `Match`, or any s1-s5 node is not sufficient. Run the probe with `--expected-route jms-s801`; it must read back the exact s801 chain before the first real part. The normal probe defaults to `--expected-route direct`. Restore and read back both saved selector values in a `finally`-style cleanup after the bounded command, including failure and interruption paths; the wrapper changes only selectors that need changing and must not use an unguarded ad hoc command.
   The provider describes s801 as a courtesy Freedom server with cheaper routing and no quality, uptime, or continued-availability guarantee: at a current multiplier `M`, it may count roughly `transferred bytes / M` against the allowance, and that multiplier may change or the server may be taken offline at any time. Treat this as provider policy, not a measured promise for Notion uploads. Never assume a multiplier of 10; it is only the provider's 20GB-download-to-2GB-counted example, and never infer upload accounting solely from that download example. Send a small bounded probe, require measured throughput that can finish inside the Notion upload expiry, then compare accepted upload bytes with the traffic-counter delta. Record the observed effective multiplier (`accepted upload bytes / counted delta`) only as an estimate because counter granularity and concurrent friends' traffic can distort it. If the counter delta is zero or too small to measure, record the multiplier as unknown rather than infinite. Every wrapped production uploader must consume `NOTION_UPLOAD_EXPECTED_ROUTE` and read the relevant selectors back before every file part; a selector change stops before the next part while preserving already accepted parts. If s801 stalls, disappears, resolves through another node, or its observed counted usage removes the expected allowance advantage, stop and return to DIRECT/deferred handling rather than silently falling through to another proxy.
   The s801 wrapper requires `--reason <text>` before it may alter selectors. State the estimated batch size or concrete DIRECT failure evidence; a generic request to use a proxy is not sufficient. The wrapper exports this audit reason to the child process. Missing or unavailable s801 must never block an ordinary DIRECT upload.
9. For large Notion file uploads, keep the upload manifest and command log. Retry the same multipart part with bounded exponential backoff for transient transport and gateway failures, and advance the manifest only after that exact part is accepted. Treat only a `409` whose message explicitly says `Failed to upload file. Please try again later.` as transient; an ordinary `409` remains a fail-closed resource conflict. If the process is interrupted, rerun the same command and resume from the accepted-part boundary instead of starting over.
   Keep AI ownership of the active upload until it reaches a terminal evidence state: poll the uploader process, its stdout/log when available, and the resumable manifest at bounded intervals. The manifest is the authoritative progress source because a host terminal may truncate or detach stdout. Each observation must record `sentParts`, `partCount`, `updatedAt`, and process existence; classify the transfer as advancing, stalled, completed, or failed. A process that has exited before the manifest says `status=uploaded` is an interrupted transfer; resume the same manifest. A manifest that says `sentParts=partCount`/`status=uploaded` while a wrapper process remains alive is upload-complete but process-cleanup-pending: wait briefly, then terminate only the exact stale uploader process after confirming no active part is changing. A manifest whose accepted part does not advance past the bounded retry/stall window is stalled; recycle only that uploader connection and resume the same file upload, never restart from part 1. Never leave a variant labelled `上传中` without an observed live process and advancing manifest, and never call a manifest-only upload complete until the destination media block is read back.
10. Probe the exact local final file and write Media Assets from `ffprobe` plus production manifest data. For series files still available locally, pass `--media-root <final-output-dir>` to the writer so `Approx Size GB` is measured from actual decimal bytes, never inferred from the spec-title range. Use a guarded batch manifest when broad title search can match sibling works. Include the exact Episode page ID because Notion may remove punctuation from the uploaded filename; after upload, prefer the observed Media Block ID for the final write or correction. Before release, read back and validate the exact Work relation, source page, Media Block ID, technical fields, measured size, and both the Media Assets `Name` and `Display Label`. For every newly created, renamed, or otherwise touched spec, both fields must exactly equal the canonical spec-page title; a correct child-page title with an empty/stale Media Assets title is a publication defect because the website may display it as `Untitled Notion page`. Repair `Name` and `Display Label` together only through an exact Work plus Media Block guarded manifest, then require direct readback and an idempotent rerun. A wrong Work relation or missing/wrong `Approx Size GB` is also a Media Assets metadata defect: repair the exact row with `tools/notion-media-assets-repair-work-relation.mjs`, then read it back. Do not create a duplicate row as a workaround.
11. Run readback or stats to prove the uploaded block and Media Assets row exist. For a manual upload with no caption, accept a sole unnamed media block only on the exact registered destination page, then persist its block ID; never guess among multiple blocks.
12. Release automation-owned Media Assets visibility gates with `tools/notion-media-assets-release.mjs`. Dry-run an exact manifest first; match Work, source page, Media Block, Episode expectation, and destination structure so the right video is exposed. `Playback Verified=true` is workflow evidence, not a demand for a human to play every file: for a normal completed upload, the exact destination-page video block and filename match, with no concrete playback fault, are sufficient to release the path. Probe the file and backfill its Media Assets row in parallel; missing/incomplete ffprobe fields are not a visibility prerequisite unless the website actually needs them to expose/open that video; do not hold a usable title for routine manual playback checks. Set `expectedEpisodeNumber` to the positive episode number for series assets and explicit `null` for movies. `Needs Review`, incomplete metadata, and follow-up issues are not playback blockers; preserve them for later repair while allowing a technically usable asset to become visible. Keep a work hidden only for an actual playback failure affecting every usable path or an explicit human visibility hold; a structure/Media Assets issue is a blocker only if it makes the wrong video play or prevents the intended video from opening.
   The Media Assets writers are fail-open for inherited visibility flags: `hideFromWebsite=true` is honored only when the manifest also carries a concrete current viewing/structure/Media Assets risk or explicit human hold. A stale checkbox or a metadata/review blocker is written as visible and remains in the follow-up record instead of blocking publication.
13. Reconcile the exact variants until the local ledger reaches `sync_ready`; this closes only the playable publication gate. Before updating the work-page handoff to `已完成`, route the exact work page through `wwp-metadata-backfiller`/`wwp-library-maintainer` and require `Metadata Status=verified`, empty `Human Issue` and `AI Issue`, and a usable maintained poster. Keep a partial series or a published-but-metadata-incomplete work `AI 处理中`, record which gate is complete and the exact metadata fields still missing, and requeue/defer the metadata task instead of calling the current release complete. If the publisher changed the page directly, immediately run `notion-workflow-handoff reconcile` for the exact work page IDs so SQLite cannot retain stale actionable states.
14. Before the local incremental website sync, determine whether this run changed only Media Assets or child blocks. Those edits may not update the parent work page's `last_edited_time`, which would leave the site cache stale. In that case append a concise `【AI(^_^) ...】` audit marker to the existing `Workflow Note` while preserving its current `Workflow Status`; this is a sync invalidation record, not a new coordination channel. Then run the local incremental website sync and query the running API with `node tools/film-website-coverage-audit.mjs --page-id <work-page-id> --title "<exact-title>" --live --json`. The live result must identify the exact source page ID; an on-disk index result is diagnostic evidence only. Visibility release requires the expected playable Episode and newly created Media Assets page IDs to appear in the running site's result. `posterPresent` and `coreMetadataPresent` are final-completion evidence, not visibility blockers: a playable work may enter the website with a missing poster or partial metadata, while those defects remain queued for repair. Bound every external poster HTTP request (default `POSTER_CACHE_REQUEST_TIMEOUT_MS=30000`); on timeout preserve an existing Azure-owned Notion poster copy, record the cache miss, and continue the playable sync instead of letting one host block the whole publication cycle. Only Notion posters copied into Azure-owned storage may be served; never fall back to temporary Notion or Douban URLs. A missing Notion poster does not stop website synchronization. A poster source that exists in Notion but cannot be fetched/cached blocks only final metadata completion, not visibility release. For a series, run `node tools/series-index-variant-audit.mjs --work-page <work-page-id> --json`: `review_required` duplicate groups must be resolved or explicitly deferred before calling the release complete. A `distinct_size_tiers` group is allowed only with current separate QC evidence. `legacy_tier_title` identifies an older playable tier whose spec omits `/集`; correct it when that spec is touched, but do not let an untouched historical label block an otherwise verified current release. Structured Media Assets related to the exact work must all reach the website index; a count that stops at a configured variant limit is a publication defect, not successful readback.
15. If film-level metadata is still missing, route to `wwp-metadata-backfiller`.
16. **Mandatory visibility action:** after the first useful path has an exact uploaded block correctly mapped to its destination page and no evidence of a viewing failure, clear the automation-owned work `Hide from Website` before website sync; then run the sync and live readback in the same bounded publication run. Missing/incomplete ffprobe or Media Assets fields are parallel backfill work, not a visibility blocker unless they actually prevent the website from exposing/opening that video. `sync_ready` and live readback confirm closure after release and must not be prerequisites for clearing the hide. If sync/readback fails, report and retry that publication step without hiding an otherwise watchable title. Do not defer visibility until metadata, People, poster, ratings, `Needs Review`, issue cleanup, or optional supplemental variants are finished. When a manifest contains blocked siblings, release the work if at least one exact playable asset passes; leave those siblings hidden and report them as independent follow-up. Keep each unfinished supplemental spec hidden at its own asset/page level until its individual upload and playback-integrity checks pass; a visible playable work may still have `Needs Review`, `AI Issue`, or partial metadata.
17. Before setting work-level `Workflow Status=已完成`, append the latest `[规格扩展:OPEN]` or `[规格扩展:CLOSED]` AI marker from the concrete ledger decision. Do not create a separate Notion property; the exact selected/deferred ledger variants remain the queryable machine queue.

## Page Shape

New API-created content should prioritize stable structure, machine parsing, and Media Assets completeness. Historical visual structures such as base/toggle/callout layouts are compatibility targets when reading old pages, not requirements for new API output.

## Guardrails

- A controller `ENOENT` means the requested local endpoint is absent, not that Notion is down or its route is non-DIRECT. A single failed controller lookup is diagnostic/in-progress evidence only; do not mark the production goal or all Notion work blocked from it. First run `node tools/with-notion-upload-route.mjs --inspect`. The shared controller helper reads the generated `clash-verge.yaml` and checks Windows' running named pipes: recent Verge service cores may expose `verge-mihomo-production-*` while the generated file still names `verge-mihomo-sidecar-release-*`. Use the uniquely discovered running core, then read the Notion selector and actual connection chain before upload. Explicit overrides remain authoritative; multiple core candidates require identifying the active one. Never hardcode a build hash, edit Clash routing, or restart the service merely to recover the old pipe name. The repository route wrapper and traffic wrapper pass the discovered controller and runtime-only authorization to the global upload transport. Keep controller secrets out of logs and reports. If discovery or controller access still fails, record it as a local controller-discovery/access blocker, retry inspection after checking the generated config and live pipe inventory, and continue independent local evidence/QC/encoding/metadata/source-audit work. Do not label it an API outage or route failure without separate API or connection-chain evidence. Clear the blocker as soon as a fresh inspection reads the active controller and `Notion` selector; then perform a bounded API check and the normal route probe before any transfer. Only a repeated, current failure of the exact required operation after discovery and bounded retry may defer that network step, and it must not suppress unrelated workflow lanes.

- Default upload is playable only; source/original-disc upload belongs to `wwp-source-archive-operator`.
- Automatic upload is the normal playable publication path. A manual-upload status is a recoverable collaboration state, not a permanent property of the variant. Every formal uploader is Direct-only by default and fails closed if it cannot read back `Notion -> 国内直连`; invoking a script directly does not disable this guard. The only non-DIRECT exception is the explicitly wrapped, audited `jms-s801` batch.
- Series collection files are disabled by default. Use one playable file per Episode page; pass the uploader's collection opt-in only after an explicit user instruction.
- Preserve the `api.notion.com` hostname for normal uploads so domain-based direct-routing rules can match. `NOTION_API_RESOLVE_IP` is a metadata/API failure workaround, not a large-upload default. A large upload must never use a proxy route, including a generic `Match` fallback, except for the explicitly selected and verified Freedom s801 batch above. Stop it as soon as Clash shows a route other than `Notion -> 国内直连 -> DIRECT` or the exact approved s801 chain.
- `--resolve-ip` is permitted only after a hostname request fails and only together with `--local-address <physical-lan-ip>` plus `--no-proxy`. Never use `--no-proxy --resolve-ip <api-ip>` alone: it bypasses only an explicit HTTP proxy, while Mihomo TUN can still capture the raw-IP socket and send it to a paid proxy group. Record the observed direct route and the fallback reason in the workflow note.
- If Clash fake-IP `DIRECT` repeatedly fails TLS while a physical-interface request succeeds, bind the uploader to the current physical IPv4 address with `--local-address <lan-ip>` and pair it with a freshly resolved real Notion API address via `--resolve-ip <api-ip>`. Verify both values at run time; never hardcode a stale LAN or Notion edge address. This path bypasses the virtual adapter and must remain direct rather than consuming a proxy group.
- If an in-flight multipart part is clearly stalled and the local Clash controller is available, close only this uploader process's exact Notion connection and retry the same `file_upload_id` plus `part_number`. Never restart all Clash traffic or discard already accepted parts. Prefer fixing hostname/direct routing first; connection recycling is a bounded fallback.
- Use `tools/lib/vpn-traffic-monitor.mjs` for route probes and automatic movie/series/package uploads. Its default interval is five minutes, with a baseline and final sample even for shorter transfers. Counter fetch failures are recorded as monitoring gaps and do not invalidate otherwise explicit `DIRECT` evidence; never retry them aggressively or delay an accepted multipart part.
- Early-created work/spec pages do not justify playable Media Assets rows; media evidence must come from a real video/file block or the exact final local file.
- Do not use work-page-root video/file blocks as final playable placement. If manual upload landed at the root, report the exact target spec/episode page and treat the block as structure-incomplete evidence. Because Notion API cannot move media blocks between pages, use manual move/reupload by the user, or explicit local-file reupload only when accepted. For future work, run the prepare-only page-creation step before encode or handoff so this cleanup is not needed.
- Do not collapse distinct Chinese audio variants into one generic spec. When filenames identify `zh-mandarin`, `zh-cantonese`, or `zh-taiwan`, prepare separate `国配`, `粤配`, and `台配` spec pages unless the user explicitly asks to merge them.
- Do not trust `Chinese`/`zh` source labels or an unverified filename marker as proof of Mandarin. If multiple Chinese streams exist and the mapping is unknown, keep the target language unconfirmed. A user listening report is valid evidence: rename/reuse the target as `粤配` when the user identifies Cantonese, and do not create a `国配` page until a Mandarin stream is independently verified.
- The workflow owns `Hide from Website` as a narrow viewing-safety gate, not as a work-completeness or perfection gate. Keep the work page visible by default, including metadata-only or not-yet-playable catalog entries. Keep an empty destination child hidden until it has media; after upload, exact page/block mapping and no concrete viewing failure are sufficient to release the path. ffprobe-backed Media Assets are required for the complete asset record and final workflow closure, but missing/incomplete fields alone do not justify hiding a video already known to play unless the website actually cannot expose/open it without those fields. Hide only the exact child with a concrete observed playback/structure failure or explicit human hold. Hide the whole work only when every usable path has a concrete viewing/structure risk or the user explicitly requests a hold. Once any usable path passes, clear any automation-owned work gate during the same publication pass even if metadata, poster, `Needs Review`, `AI Issue`, or `Human Issue` still needs later repair. If impact is uncertain or limited to a non-blocking defect, publish and record follow-up. A verified `国配` branch requires no Chinese subtitle for release; record missing subtitles as optional later enrichment and do not keep the branch hidden for that reason alone.
- Optional planned high/balanced bitrate, alternate audio, subtitle, commentary, or cut variants do not keep an otherwise watchable work hidden. Release the work once one uploaded video is mapped to its exact work/spec/episode page and there is no concrete evidence that normal users cannot watch it. This is the minimum visibility gate, not the stricter `sync_ready`/final-completion gate; finish Media Assets, ledger, sync, and readback afterward. Gate later variants individually.
- Apply upload, `ffprobe`, QC, and ledger gates to the exact media child path they prove; do not make them a blanket work-level release gate. The work page is visible by default, and when it is hidden, clear the work-level flag as soon as at least one correctly mapped published path has the evidence needed to establish normal viewing (exact destination page/block, matching Media Assets row, and no concrete playback failure). Do not wait for every episode/spec, every optional QC task, or final `sync_ready`/`已完成` bookkeeping when that does not change the user's ability to watch. Keep only an empty, mismapped, or concretely unsafe child hidden; record uncertainty and repairable defects as follow-up. For a partial series, verified sibling episodes may release while an uncertain episode stays isolated. Preserve human plain-text notes and acknowledge them with a later AI marker. **Do not keep an otherwise playable work hidden because of metadata, poster, rating, People, review, naming, or optional-spec defects.**
- Set or keep `Needs Review` when upload/readback evidence is incomplete, Media Assets disagree with the page, subtitle/audio/QC is uncertain, or a human decision is pending. `Needs Review=true` does not block visibility for a correctly mapped path that does not affect normal viewing; keep the review flag and publish that path. Do not clear review merely to publish, and do not hide merely because review remains open.
- Do not infer codec, duration, frame rate, audio, subtitles, or resolution from filenames when final media can be probed.
- Do not treat an accepted final multipart part as publication completion. The file upload must be completed, the media block appended to the exact destination, Media Assets written and read back, the ledger reconciled to `sync_ready`, and the live site queried successfully.
- Configure website ingestion to retain the complete expected Episode set for every specification. Relation-bounded structured Media Assets must bypass the legacy `NOTION_VARIANT_LIMIT` block-scan cap and be sorted without slicing; keep the cap only for defensive legacy child-block fallback scanning. Verify continuity and specification coverage as well as total count so a newly added Episode cannot silently evict an older one.
- Do not mark the current workflow `已完成` from local logs, `sync_ready`, or Media Assets readback
  alone; require exact metadata verification plus live playable, poster, and
  core-metadata readback. This completion rule is separate from website visibility: a playable work may sync before the metadata task is complete.
- Do not require a persistent Asset URL for Notion-hosted uploads when the URL is a temporary signed file URL; durable page/block IDs are the stable proof.

## Bounded Naming Checks

- Spec-title consistency checks are targeted follow-up work, not a reason to enumerate the full library.
- Inspect only the exact specs touched in the current run or the latest small set of production/upload targets, normally no more than 3. For series, verify that the title uses a per-episode size or range such as `0.8-1.0GB/集`, never the season total.
- Within that bounded set, normalize every touched sibling spec to the same token order and vocabulary. A touched work must not retain a mix of full bilingual parent titles, English-only titles, omitted codecs, bare language names, or ambiguous `中文原声` labels when the facts are known.
- Do not use a recent-page watcher or broad title search to discover more naming problems. If an older spec was not touched, leave it alone unless the user names it or a later workflow step reaches it.

## AI Age Advisory and Website Publication

AI age suggestions are nonblocking reference information. Missing suggestions, low confidence, a recommended minimum age, or `需人工复核` must not set `Needs Review`, set `Hide from Website`, block website publication, or keep a verified publication pending in the Ledger. Keep the suggestion, confidence, reason, and risk tags in the family-age fields for later review. Do not put age-only advisory findings in `AI Issue`. Core metadata completeness does not require AI family-age fields. Existing age-only `AI 年龄建议待复核：` findings may be retired; preserve unrelated AI findings, `Human Issue`, and other concrete review reasons. Apply normal publication readiness rules after retiring an age-only gate; preserve user-set hide decisions and media/QC/identity gates.
